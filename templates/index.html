What deploy.sh does on the server

  1. Install the Python packages into the venvpip install -r requirements.txt
  2. Remember which commit this isecho $SHA > REVISION
  3. Create the table if it is missingmysql chatapp < schema.sql
  4. New Nginx snippet, old one back if the test failsnginx -t || mv .bak
  5. Install the unit and restart only the chatsystemctl restart chatapp
  6. Ask the socket which version is running/health == $SHA

The runner then checks the same /viikko5/health from the public address, plus the chat form and app.js. rsync skips REVISION and static/gifs, so they survive every deploy.

Three choices I had to think about

The env file is 600, not 640 like in the course material

Nginx needs the chatapp group to open the socket. With 640 that group could also read the database password. With 600 only root can, and the app still gets the values because systemd reads the file as root before it starts the service.

The deploy user has full sudo

I thought about a separate user with a short sudoers list. But the deploy installs the systemd unit from the repository, and whoever can change that file can run anything as root. A short sudo list would only look safer. What protects the server is the separate deploy key (one line to delete from authorized_keys), GitHub secrets, two-factor login on my GitHub account, and deploys only from main.

Port 22 is open to everyone

GitHub's runners don't have fixed IP addresses, so the cPouta security group allows SSH from anywhere. The server only accepts key logins, so the open port mostly means that scanners can see it. The other options were a self-hosted runner, or a rule for GitHub's whole published IP list, which is long and keeps changing.

Adding /viikko5/ to Nginx

Weeks 1 to 3 share one Nginx site. I didn't replace it. I added two lines by hand, after a backup to ~/default.ennen-viikko5:

/etc/nginx/sites-available/default
 server {
     listen 80 default_server;
     root /var/www/html;                        # week 1, week 3
     location /viikko2/ { proxy_pass http://127.0.0.1:5000/; ... }
+    # Viikko 5: chat app (deploy.sh updates the snippet)
+    include snippets/chatapp.conf;
 }

The snippet comes from deploy/nginx/chatapp.conf and only has three location blocks:

RequestWhat Nginx does
/viikko5Redirects to /viikko5/
/viikko5/static/…Serves the file from disk with alias, Flask is not involved
/viikko5/…Sends it to the socket without the prefix. X-Forwarded-Prefix lets Flask build links that start with /viikko5.

^~ on the locations means the site's regex locations are never tried for these paths. Every deploy runs nginx -t before reloading and restores the previous snippet if the test fails, so a mistake in this file can't take weeks 1 to 4 down.

Database and replication

MySQL, not MariaDB. Server A already runs MySQL 8.4 for week 2 and as the source of week 4's replication. Installing mariadb-server would remove mysql-server and break both. The app uses PyMySQL, which talks to either, so the chat got its own database in the MySQL that was already there.

laskuri A B replicated, week 4
chatapp A ✗ B stays on A

Before creating the database I added one line to B's replikointi.cnf:

replicate-wild-ignore-table = chatapp.%

The messages are private chats, and B is only there to show the week 4 counter. After the change B listed only laskuri and the system databases, and both replica threads were still Yes.

More details
  • I used the wild form because replicate-ignore-db looks at the default database of a statement, so CREATE DATABASE chatapp could have slipped through.
  • The MySQL account chatapp still shows up on B, because accounts live in the mysql system database. It has no database there and B is super_read_only, so it can't do anything.
  • The table is messages(id, session_id, role, content, created_at) with an index on (session_id, id).

Problem I solved

The chat worked fine, but every start left this in the log:

[ERROR] Control server error: [Errno 13] Permission denied: '/home/chatapp'
Cause
Gunicorn 25.1 added a control socket that goes to $HOME/.gunicorn/ by default. My requirements.txt said only gunicorn>=23, so the server got 27.0.1. The service user has no home, and ProtectHome=true hides /home anyway.
Fix
I don't use the control tool, so I switched it off in the unit and let the pipeline deploy it:
deploy/systemd/chatapp.service
 ExecStart=/opt/chatapp/venv/bin/gunicorn \
     --workers 2 --worker-class gthread --threads 8 \
     --timeout 300 \
     --bind unix:/run/chatapp/gunicorn.sock --umask 007 \
+    --no-control-socket \
     --access-logfile - \
     app:app

Lesson: read the logs even when everything works. A version range with no upper limit can bring new defaults that clash with the hardening.

A smaller one: I first put the include line inside location = /viikko2. nginx -t passed only because the snippet was still empty. It would have failed on the first deploy, so I moved it to the server level.
